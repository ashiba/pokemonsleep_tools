# PR Creator

このスキルは、OpenCode が PR を作成する際に `.github` 配下のテンプレートとリポジトリの運用ルールに従ったフォーマットを守るためのガイドである。

## 目的

- `.github/pull_request_template.md` に準拠した PR 本文を生成する
- 変更の背景・意図を明確にし、レビュアーの負荷を下げる

## 前提確認

1. `.github/pull_request_template.md` を必ず読み込む。テンプレートの見出し・順序を崩さない。
2. `.github/ISSUE_TEMPLATE/issue.md` の「目的 / 内容 / 対象」構成も把握し、関連 Issue があれば対応関係を明記する。
3. `AGENTS.md` の運用ルール（コミットメッセージ・PRテキストは日本語、`feature/*` ブランチ運用）に従う。

## PR 本文フォーマット

- `.github/pull_request_template.md` を毎回読み込み、その見出し・順序・構成を厳守する。スキル内にテンプレート本文の具体例をハードコードせず、常に実ファイルを正とする。
- PR 本文は簡潔さを保つ。通常50行未満、長くても100行未満を目安とし、冗長な説明は削る。必要な情報（変更内容・背景・注意事項・close #・変更カテゴリ・レビュー観点）は漏らさない。

### 各セクションの記載指針

#### 1. `# 変更内容`
- どんな変更を行ったかを箇条書きで具体的に書く
- 主要な変更カテゴリを明記する。例: `依存更新 / 機能追加 / リファクタ / 修正 / 削除` から該当するものを選択し、必要に応じて複数記載
  - 例: `変更カテゴリ: 機能追加`
  - 複数に跨る場合は `変更カテゴリ: 機能追加, リファクタ` のように列挙
- UI 変更がある場合は対象ページ（料理サーチ / レシピ食材チェッカー）を明記

#### 2. `# 背景`
- なぜこの変更が必要だったかを書く
- 関連 Issue の「目的」「内容」を要約し、どんな理由でこの対応を選んだかを説明
- Issue がない場合でも、ユーザーの依頼や不具合の再現条件を記載

#### 3. `# 注意事項`
- マージ時の影響範囲、互換性、マイグレーション要否、既知の制限事項があれば必ず書く
- 特になしの場合でも `特になし` と明記し、空欄にしない

#### 4. `close #<番号>`
- 関連 Issue をクローズする場合は `close #<番号>` を末尾に付与
- 複数ある場合は `close #1, close #2` のように列挙

## 追加で含める項目

テンプレートの 3 セクションに加え、PR 本文内で以下を必ず補足する（見出しは `# 変更内容` 内または `# 注意事項` の直後に `## レビュー観点` として追記）:

### レビュー時に重点的に確認してほしい点
- `## レビュー観点` 見出しを設け、レビュアーに注目してほしい箇所を箇条書きで書く
- 例:
  - ロジックの正確性（判定仕様・フィルタ条件など）
  - UI/表示崩れ（PC/モバイル、カテゴリ絞り込み時）
  - データ整合性（`food/` 配下の JSON との整合）
  - 例外・空状態の扱い

## 作成手順

1. `git status` / `git diff --staged` / `git diff main...HEAD` / `git log --oneline -10` で差分と文脈を把握する
2. `.github/pull_request_template.md` を読み、テンプレートを雛形にする（スキル内のハードコードを参照しない）
3. 上記の「各セクションの記載指針」に従い、日本語で本文を埋める
4. 変更カテゴリとレビュー観点を漏れなく記載したか自己チェックする
5. PR 本文が通常50行未満・長くても100行未満か確認し、冗長な説明を削る
6. タイトルも日本語で、変更内容を要約したものにする（例: `レシピ食材チェッカーに作れる件数表示を追加`）

## 禁止事項

- テンプレートの見出し（`# 変更内容` / `# 背景` / `# 注意事項`）を削除・リネームしない
- 英語のみの PR 本文にしない（リポジトリルールにより日本語が必須）
- 変更理由やレビュー観点を省略しない

## チェックリスト（提出前に確認）

- [ ] `.github/pull_request_template.md` のフォーマットに準拠している（スキル内の具体例ではなく実ファイルを参照した）
- [ ] どんな理由でどんな変更を行ったかが書かれている（背景 + 変更内容）
- [ ] 注意事項が書かれている（なければ `特になし`）
- [ ] レビュー時に重点的に確認してほしい点が `## レビュー観点` に書かれている
- [ ] 主要な変更カテゴリ（依存更新 / 機能追加 / リファクタ / 修正 / 削除）が明記されている
- [ ] 日本語で書かれている
- [ ] 関連 Issue がある場合は `close #<番号>` が末尾にある
- [ ] PR 本文が簡潔か（通常50行未満、長くても100行未満を目安に冗長部分を削っている）
